The SQL Rewrite That Cut a Daily Job From 90+ Minutes to Under 10 — and Why It Matters

The Moment I Realized Something Was Off

Slow pipelines rarely fail loudly. They creep.

A daily job I owned — one that created a binary flag to identify a specific user web activity pattern — had always run smoothly. The logic was correct, the output fed multiple dashboards, and no one complained.

But as traffic grew and more parallel workloads ran on the same Snowflake warehouse, I noticed something worrying:

👉 On certain days, the job would climb to almost two hours.
👉 Especially on mornings when two or three heavy processes overlapped.

A two-hour transform just to generate a per-user flag?
My instinct said: No. That’s not normal.

Something needed to change.

The Rewrite That Changed Everything

The original implementation used a self join:

  • Step 1: identify the “qualifying” row per user (based on a business metric).
  • Step 2: join back to the main table to flag that row (flag = 1).
  • Step 3: mark everything else flag = 0.

It worked — but it was compute-heavy, doing unnecessary comparisons, shuffles, and row duplication.

Original (slow) pattern using self-join:

CREATE OR REPLACE TABLE user_web_flags AS
SELECT a.*,
       CASE WHEN a.event_time = b.qualifying_event_time THEN 1 ELSE 0 END AS flag
FROM web_events a
JOIN (
    SELECT user_id,
           MIN(event_time) AS qualifying_event_time
    FROM web_events
    WHERE event_type = 'target_event'
    GROUP BY user_id
) b
  ON a.user_id = b.user_id;

This read the table twice, created a large intermediate table, and caused row expansion.
As volume grew, the job ballooned to ~90 minutes (sometimes more).

The Fix: CASE + Window Function (No Join Required)

I stepped back and asked a simple question:

“Why join at all? Can’t Snowflake identify the first qualifying row within the same scan?”

It can.

Using a window function (ROW_NUMBER()) plus a CASE expression, we can compute the flag per user in a single pass — no join needed.

New (fast) pattern using window function + CASE:

CREATE OR REPLACE TABLE user_web_flags AS
SELECT *,
       CASE WHEN ROW_NUMBER() OVER (
                PARTITION BY user_id
                ORDER BY event_time
            ) = 1 
            AND event_type = 'target_event'
       THEN 1 ELSE 0 END AS flag
FROM web_events;

This does three things extremely efficiently:

  1. Orders each user’s rows.
  2. Identifies the first qualifying row.
  3. Flags it — all in the same query, no duplication, no join.

Runtime dropped from ~90 minutes to under 10.
Same logic. Same output. Zero compromise on business metrics.

Three More Snowflake SQL Fixes That Saved Us Hours

After that experience, I revisited other queries and found similar patterns waiting to be improved. Here are three that made meaningful differences — without touching hardware or scaling warehouses.

1) EXISTS Instead of JOIN When You Only Need Membership

Problem:
A query joined users to a large purchases table just to check whether a user had any qualifying purchase — causing row explosion.

Slow version (JOIN):

SELECT u.*
FROM users u
JOIN purchases p
  ON u.user_id = p.user_id
WHERE p.amount > 100;

Faster version (EXISTS):

SELECT u.*
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM purchases p
    WHERE p.user_id = u.user_id
      AND p.amount > 100
);

Why it’s better:
EXISTS short-circuits and avoids producing duplicate rows.
Less shuffle. Less data processed. Faster.

2) Incremental MERGE Instead of Reprocessing Entire History

Problem:
A nightly job recomputed all historical data daily — scanning the entire table.

Better pattern:

CREATE OR REPLACE TABLE staging_events AS
SELECT *
FROM raw_events
WHERE event_date = CURRENT_DATE();
MERGE INTO analytics.flags t
USING staging_events s
ON t.event_id = s.event_id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT (...);

Why it’s better:
You process only the new rows, not the entire table.
Compute drops drastically.

3) Use Clustering + Predicate Pushdown for Date-Heavy Queries

Problem:
Query scanned billions of rows because the table wasn’t clustered on the filter column.

Fix:

ALTER TABLE analytics.events CLUSTER BY (event_date);
SELECT user_id, COUNT(*)
FROM analytics.events
WHERE event_date BETWEEN '2025-11-01' AND '2025-11-30'
GROUP BY user_id;

Snowflake prunes micro-partitions aggressively when clustered correctly.
Less data scanned → faster queries.

A Short Checklist I Now Use Before Calling Any Query “Slow”

  1. Am I scanning the table multiple times unnecessarily?
  2. Is there a join I can replace with a window function or EXISTS?
  3. Can I avoid reprocessing history and use incremental patterns?
  4. Are my predicates pushing down early?
  5. Are my partitions or clustering keys aligned with my filters?
  6. Have I validated output correctness after every optimization?
